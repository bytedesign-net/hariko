### 7.1 Manual test procedures

**Applies to all rows** — run against the §1 fixture URLs: `/` · `/2026-11-08/test-post-1/` (sidebar) · `-2` (full width) · `-3` (sticky) · `/about-2/` · page templates `page-with-sidebar` / `page-fullwidth` · `/products/` · a deliberately wrong URL for 404 · `/?s=test` for search results. Record PASS/FAIL in the §5/§7 cells; file every FAIL as a new `F-xx`/`D-xx` row in §8.

**M-01 — NVDA (Windows; Firefox recommended, Chrome optional)**
1. Install NVDA (nvaccess.org, defaults fine). Open **Speech Viewer** (NVDA menu → Tools) so every utterance can be re-read.
2. Per template URL: load, press `Ctrl+Home`, then audit with quick keys:
   - `Insert+F7` → *Landmarks* tab: order must be banner → navigation → main → (search region only where a Search block exists: sidebar pages, 404, search) → contentinfo. Hero + post list must sit **inside main** (F-03 evidence).
   - `Insert+F7` → *Headings* tab: posts on home = H2, singular title = H1, no skipped levels; footer's 3 nav list headings present (§5 row 5).
   - `H`/`Shift+H` steps headings, `D`/`Shift+D` landmarks, `B`/`Shift+B` links — listen for unlabelled noise (`link, ,` = §5 row 12 FAIL).
   - `Tab` from the top: the **skip link is the first announced focus**; order matches visual order; submenu toggles announce expanded/collapsed; no focus trap; `Shift+Tab` retraces symmetrically.
   - Read one post with `↓` arrows: date announced as a human date with the en-dash (no digit stutter), comment link announced with post context, sticky post (`-3`) announced identically to a normal post (A-19).
3. Target feel (2.5.8, keyboard side): `Tab` to every visible control — each gets focus exactly once with an audible name+role (the 24 px toggle fix F-02 is pointer-side; pointer/touch side is M-03).

**M-02 — VoiceOver (macOS; Safari)**
1. `Cmd+F5` starts VO. In VoiceOver Utility → Verbosity → Web Page, enable “announce web page stats on load” (heading/link/landmark counts).
2. Same audit as M-01 using VO equivalents: `VO+U` rotor → *Landmarks* (order) and *Headings* (levels); `VO+Cmd+H`/`VO+Shift+Cmd+H` step headings; `Tab` for focus order — skip link announced first; `VO+↓` reads a post through for the date / comment-link / sticky rows.
3. Repeat on all templates; also run Safari's rotor *Form Controls* on the sidebar page to confirm search input + button both have names.

**M-03 — VoiceOver (iOS) + TalkBack (Android): touch feel**
- iOS (Settings → Accessibility → VoiceOver, via Accessibility Shortcut triple-click; Safari), iPhone SE-class 320 pt width:
  - One-finger swipe through home → open menu → one post once: landmark announcements at each boundary; **double-tap lands on the intended target every time** — having to search for a target, or hearing the neighbouring element read first, means the target/spacing is too small.
  - Double-tap the submenu toggle, search submit, comment form fields; footer's 3 lists read as lists with N items.
- Android (TalkBack via Settings → Accessibility or both-volume-key hold; Chrome):
  - **Touch exploration**: drag a finger across the header nav and post meta, lift — TalkBack must read the element actually under the finger; ambiguous reads between adjacent items flag < 24 px targets or < 8 dp spacing.
  - Double-tap submenu toggle (F-02) / search / comment submit; expanded state announced; “Banner/Main landmark” wording matches the §5 order.

**M-04 — Ctrl++ visual check only** (the mobile-width half of this row is already covered by automated A-16 at 320 px)
1. ~1280 px desktop window, `Ctrl+0` to reset, then `Ctrl++` to **150% / 175% / 200%**; on each: home, post-with-sidebar, `products`, 404, search results.
2. Check by eye: no clipped or overlapping text; header nav wraps or collapses without losing items; sidebar stacks under content instead of crushing the main column; footer columns stack; **no page-level horizontal scrollbar** (scroll inside genuinely wide content would be acceptable — hariko has none); `Tab` to the skip link at 200% and confirm it is visible, not pushed off-screen.
3. Spot-continue to 400–500% as a cheap 1.4.10 sanity pass: still one column, still no body-level horizontal scroll. (Note: browser zoom is not identical to WCAG's reflow metric — A-16's viewport emulation stays the authoritative check.)

**M-05 — Forced colours (Windows high contrast / contrast themes)**
1. Settings → Accessibility → Contrast themes — test at least **one dark (e.g. Aquatic) and one light (e.g. Desert)** theme; toggle with `Alt+Left+Shift+PrintScreen`. Fast pre-triage without OS settings: DevTools → Rendering → *Emulate CSS media feature forced-colors*. Also try Edge, which auto-enters forced colours.
2. hariko ships **no `forced-colors` overrides** (verified by grep over `assets/css/` + `theme.json`), so the expected behaviour is: browser forces every colour to system colours and the theme stays fully usable. On home, post-with-sidebar, 404, search results, and a post with the comment form:
   - `Tab` through: focus ring (theme draws `outline: 3px` + 6 px offset halo) must remain **visible in the forced system colour**, never erased.
   - Links in running text stay identifiable **without colour** — the F-01 underlines must survive the forced palette.
   - Buttons and form controls (search submit, comment form inputs/submit) keep a visible box/boundary and a visible focus state when backgrounds are forced to Canvas/ButtonFace.
   - Nav submenu toggle arrows (`currentColor`) stay visible at narrow and wide widths.
   - Hunt for invisible text (hero Cover, post meta line, sticky post `test-post-3`): since no `forced-color-adjust: none` exists in the theme, any region that keeps its own colours while the rest is forced is a new defect → §8.

**M-09 — Editor a11y (wp-admin → Posts → Add New, screen reader on)**
1. `Tab` from the very top of the editor document: core skip links (“Skip to toolbar”, “Skip to main content”, …) are announced and land correctly — the theme must not break or hide them; visible focus is never `outline:none`.
2. Heading picker: focus a paragraph, open the level dropdown by keyboard (toolbar → `F6`/arrows); options read as real levels — theme offers **H2–H4** only (H1 belongs to content titles); insert one of each and confirm the block announces “heading level N”.
3. Palette names: open the Text/Background colour pickers — every swatch reads a meaningful name per `theme.json` (Slate, Amber, Cocoa, Crimson, …), not “colour 1/2”; cross-check the names against the readme palette list.
4. Contrast sanity: pick the text/background pairs actually used by the theme (e.g. body text on `base`) and confirm the editor renders the same values the front end uses — i.e. pairs already audited in §6 (A-01/A-14 evidence); free-picked custom colours are outside the theme's claim.
5. Editor ↔ front-end parity (`add_editor_style`): a post with H2–H4, an in-text link (underlined, not colour-only), and a quote should look the same in the editor canvas as on the front end, so the non-colour cues (WCAG 1.4.1) are seen while authoring too.
